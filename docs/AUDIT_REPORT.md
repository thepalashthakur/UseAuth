# UseAuth project audit

**Audit date:** 2026-10-25. **Scope:** repository, lockfile, local automated checks, public production health endpoint, and Vercel environment-variable names. No application code, database, Supabase settings, or deployment was changed. “Verified” below means both implementation and a relevant executed check; mocked tests do **not** establish that an email or Supabase flow works in production.

## Executive assessment

UseAuth is an operational email/password facade over one Supabase Auth project. It has hosted pages and a separate bearer-token API. It is **not yet a multi-application SSO or authorization platform**. A shared `auth.users` table gives a shared identity namespace, but does not create application sessions, client-bound tokens, or application access grants. The production health endpoint reports required variables present; it does not test Supabase connectivity or email delivery.

The immediate priorities are to patch audited dependencies, inspect the live database and Supabase Auth settings, then verify the existing flows with real accounts. New OAuth clients and SDKs should follow an application access model, not precede it.

## Evidence and limits

- Repository on `main` at `c682fd4`, clean at audit start. npm lockfile is present; no other package-manager manifest, `vercel.json`, `supabase/config.toml`, generated database types, or local `.env.local` is present.
- Executed `npm test`: 48/48 pass in four files. Executed `npm run typecheck`: pass. Existing tests mock Supabase. CI runs `npm ci`, lint, typecheck, tests, and build in `.github/workflows/checks.yml`; no database-backed or browser flow is in CI.
- Executed `npm audit --json`: 6 affected packages (1 critical, 3 high, 2 moderate). This is a dependency advisory result, **not** proof that every vulnerable code path is reachable in UseAuth.
- Vercel lists production `RECOVERY_GRANT_SECRET`; `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `APP_URL` target production, preview, and development. `AUTH_ALLOWED_ORIGINS` is absent. Values and secrets were not retrieved. `GET https://use-auth-rosy.vercel.app/api/health` returned `status: configured`, with Supabase and recovery configuration checks true.
- A Supabase CLI exists, but the repository has no linked project and its read-only `supabase projects list` returned no metadata (exit 137). No direct database connection or Supabase dashboard access was available. **Live schema, RLS, OAuth Server enablement, JWT signing algorithm, Auth policies, email templates, SMTP, and redirect lists remain unverified.** The user's statement that applications share a Supabase database is treated as project context, not a database inspection result.

### Controls already present

Hosted cookies are HttpOnly and SameSite=Lax; production cookies are Secure. Cookie mutations require same-origin `Origin` and reject `Sec-Fetch-Site: cross-site` (`auth-handler.ts:62-71`). Token endpoints do not enable credentialed CORS. Inputs are strict Zod objects; JSON bodies are bounded to 16 KB; auth responses are non-cacheable and avoid echoing provider errors. `/me` uses Supabase `getUser` rather than trusting decoded browser claims. The reset grant is HMAC-bound to the recovery access token/user and expires in ten minutes. No secret/service-role key or custom password hashing is in application code. These controls are supported by mock tests, not a penetration test.

### Open security checks

No live verification was possible for session fixation, JWT issuer/audience enforcement in consumer apps, RLS policy enforcement, provider rate limits, email enumeration behavior under actual Supabase settings, OAuth state/PKCE, token replay after password change, or security log redaction. OAuth state/PKCE is currently **not implemented**, so those tests belong to the later integration phase.

## Database inventory from repository

- `auth.users`: managed by Supabase; referenced by migration, but live schema not inspected.
- `public.usernames`: `user_id` primary key and FK to `auth.users(id)` with cascade delete; unique normalized `username`; format check. RLS enabled; table privileges revoked from `anon` and `authenticated` (`supabase/migrations/20261006000000_unique_usernames.sql:2-9`). No table RLS policies in this migration.
- `public.sync_username()`: `SECURITY DEFINER`, fixed empty `search_path`, trigger after insert or metadata update on `auth.users`; syncs reservation. Migration backfills existing metadata; duplicate/invalid existing data needs preflight before applying (`:11-46`). Live trigger owner and installed state not verified.
- `public.username_available(text)`: `SECURITY DEFINER` RPC, execute granted to `anon` and `authenticated`, reveals only availability (`:48-62`). Its live permissions and behavior were not checked.
- No repository definition for app registration, membership, permissions, profiles beyond metadata, or audit events. The absence from Git **does not prove** they are absent from the shared production database.

## Technical debt and integration risks

The shared `auth-handler.ts` combines routing, validation, provider calls and response shaping, which complicates policy insertion. A consuming app must currently handle raw bearer/refresh tokens itself; the README recommends backend storage but no SDK enforces it. Recovery `return_to` is an origin allowlist, not an OAuth redirect registry. `AUTH_ALLOWED_ORIGINS` is absent in Vercel, so intended app-specific recovery returns are not configured. CI has no live provider, RLS, browser, or deployment smoke test. `/api/health` is a configuration check rather than a dependency probe. Production settings such as email templates, SMTP, Supabase Auth rate limits, JWT signing key, and session lifetime remain unverified.

## Recommended sequence

1. Patch vulnerable packages and run regression checks; do not assume audit counts equal reachable exploits.
2. Obtain read-only Supabase metadata/settings and inventory every existing app and RLS dependency before any migration.
3. Verify the existing hosted and API flows end to end, including expired sessions and reset/logout failure paths.
4. Define per-app membership and enforcement, then pilot Supabase's native OAuth 2.1/OIDC server with one client and explicit consent.
5. Add SDK/adapters, security logging, abuse controls, and staged consumer migrations.
